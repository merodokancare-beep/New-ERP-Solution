[Heading 1] Document Control
[Heading 1] 1. Purpose
[Normal] This document defines the functional structure, navigation, workflows, controls, reporting requirements and implementation guidance for the SDK Solutions ERP. It is intended to serve as the master functional baseline for UI/UX design, backend development, database design, testing and future enhancement.
[Heading 1] 2. Design Objectives
[List Bullet] Simple top-level navigation with grouped business functions.
[List Bullet] Complete end-to-end transaction flows rather than isolated menus.
[List Bullet] A project-centric operating model connecting clients, projects, sales, procurement, delivery, expenses and collections.
[List Bullet] Scalability for future modules without redesigning the core architecture.
[List Bullet] Strong financial controls, auditability and approval workflows.
[List Bullet] Centralized master data to avoid duplicate records.
[List Bullet] Clear separation between internal office inventory and fixed/durable assets.
[Heading 1] 3. Scope
[Normal] The ERP covers management dashboards, centralized masters, project management, sales and billing, procurement, internal office inventory, accounts and payments, GST/tax, cash and banking, payroll/employees, reports/analytics, administration, assets and support.
[Normal] The Office Inventory module is specifically for items purchased for internal organizational use. It is not a customer-sales inventory or commercial warehouse management system.

[Normal] Purchase Bill → Vendor Payable → Payment Request → Approval → Payment → Bank/Cash → Vendor Ledger.

[Heading 2] 10.4 Accounting Posting Principle
[Normal] The accounting engine should automatically generate balanced debit/credit entries from posted transactions. Financial transactions should not be deleted; corrections should use cancellation, reversal or adjustment mechanisms subject to permissions.

[Heading 1] 31. Final Architecture Summary
[Normal] The recommended ERP is a project-centric business management system with a connected chain rather than a collection of independent menus.
[Normal] Core revenue chain: Client → Project → Sales → Invoice → Collection.
[Normal] Core cost chain: Project → Procurement → Office/Project-related consumption → Delivery → Expense → Vendor Payment.
[Normal] Financial integration: Sales/Purchase/Expenses/Payments → GST & Tax → Accounts → Cash/Bank → Project P&L → Management Reports.
[Normal] The design deliberately keeps Office Inventory lightweight because its purpose is internal office stock. Commercial warehouse, batch, serial and customer-sales inventory functionality should not be introduced unless the business scope later requires it.
[Heading 1] 32. Conclusion
[Normal] This specification provides the functional baseline for designing and developing the SDK Solutions ERP. The supplied ERP structure is retained while clarifying the transaction relationships, financial controls, office-inventory scope, approval framework, audit requirements, technical architecture and implementation boundaries.
[Normal] Before production development begins, this document should be followed by detailed UI screen specifications, an ERD/database schema, API specification, accounting posting matrix, GST technical specification, report layouts and a complete UAT test plan.
